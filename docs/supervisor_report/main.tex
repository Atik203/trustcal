\section*{1. Project update}

Three heterogeneous LLMs answer the same scientific multiple-choice question, read one another's reasoning over three rounds, and revise. The treatment arm (B8) aggregates the final answer with trust weights computed from how well each agent's claims check out against retrieved external evidence (PubMed, arXiv, Semantic Scholar); the control arm (B8-no-trust) runs identical prompts, evidence, and source partitioning but aggregates by majority vote. The failure under study is \emph{sycophantic consensus}: a confidently wrong majority pressures a correct minority agent into agreeing, after which the vote records the wrong answer as consensus. The confirmatory endpoints (accuracy and Correct-Minority Retention on pressure-eligible items) are frozen in the pre-registration; no result below claims them.

\section*{2. Results}

\textbf{Setup.} Three heterogeneous 4-bit models are served by vLLM 0.34.0 on one 96\,GB RTX PRO 6000 with an 8192-token context: Qwen3.8-27B-AWQ-INT4 (agent 1), Gemma-4-26B-A4B-AWQ-4bit (agent 2), and Mistral-Small-3.2-24B-AWQ (agent 3). Every debate runs three rounds at temperature 0.7. Each agent's answer is parsed into claims; claims are routed by domain to PubMed, arXiv, Semantic Scholar, and OpenAlex; retrieval is progressive (half depth in rounds 1--2, full depth in round 3) and sources are partitioned across agents so no agent sees another's evidence set. A lexical verifier scores every claim against the retrieved passages (support / refute / insufficient). B8 turns those verdicts into trust weights \emph{during} the debate; the control runs identical prompts, evidence, and partitioning and aggregates by majority vote.

\textbf{Engineering gates (readiness, not findings).} P0 gate 13/13 passed; 661 local tests green. University 18\,GB slice checks (one 8--9\,B model plus two mocks; Q4\_K\_M main-model templates) return schema-valid records. These prove the pipeline is built correctly; they say nothing about whether trust-weighting works.

Two findings came out of the smoke itself. First, one injection item showed a \emph{transient} effect the check initially missed: the targeted agent moved D\,$\to$\,C under the injected consensus in round 2, then reverted to D by round 3. The smoke check compared only round 1 with round 3, so it reported a failure on a real delivered effect; the check now detects any post-injection change, with a regression test, and injection passes 5/5. Second, the oracle arm's fifth record was lost to a spot eviction, not to the pipeline; the 4 completed records are all valid and all final answers correct.

\textbf{FP8 precision smoke: passed.} The 73.68\,GB FP8 stack serves all three models together (5/5 valid records, 3 rounds). Serving needed one config fix first: FP8 weights are roughly twice the 4-bit size, so the 8192-token context left no room for KV cache; context is 4096 with max 16 concurrent sequences per server (worst-case prompt 2438 tokens $<$ 3072 available, verified by preflight).
